# 副食品紀錄與試敏表（整合 babyfoodie）— 設計

- 日期：2026-10-29
- 狀態：已核可並實作（2026-10-29）
- 範圍：web（PWA）+ 同步伺服器
- 來源：[babyfoodie](https://github.com/wsturkey6-hash/babyfoodie) 的 SPEC.md（2026-09-19 版）。功能照搬，畫面改用 BabyMonster 風格

## 1. 目標

把 babyfoodie 的兩個功能搬進 BabyMonster，之後只維護一個 App：

1. **副食品紀錄**：日期時間、吃了哪些食材、份量、有沒有反應
2. **試敏表**：4～10 個月可嘗試的 118 項食材，依建議順序排列，用顏色加圖示標出「未嘗試／已嘗試／有反應」

搬進來之後自動得到 babyfoodie 沒有的三件事：**兩位家長同步**、**多寶寶**、**備份檔**。

## 2. 已確認的決策

| 議題 | 決定 |
|---|---|
| 分頁位置 | 合併「每日統計」與「趨勢」成一個「統計」分頁，空出的位置給「副食品」。分頁總數維持 5 個 |
| 設計風格 | 一律用 BabyMonster 現有風格（`web/src/ui/styles.css` 的色票與元件），不帶入 babyfoodie 的貼紙手帳風 |
| 舊資料 | **不搬**。babyfoodie 在 localStorage 的資料不匯入，從頭開始記 |
| babyfoodie 網站 | 新功能上線後關掉 GitHub Pages |

## 3. 分頁調整

### 3.1 新的底部分頁列

```
之前：記錄｜每日統計｜趨勢｜疫苗｜設定
之後：記錄｜統計｜副食品｜疫苗｜設定
```

- 「副食品」放第三格，緊接在日常會用的兩個分頁後面；疫苗、設定不常用，維持在右邊
- 副食品圖示：新增一個碗＋湯匙的線條圖示到 `components/icons.tsx`，筆畫與現有圖示一致

### 3.2 「統計」分頁

把 `DailyStatsPage` 和 `TrendPage` 放進同一個分頁，上方用現有的分段切換元件（趨勢頁「日常趨勢／生長曲線」用的那一個）切成三種模式：

```
[ 每日 ][ 趨勢 ][ 生長曲線 ]
```

- **每日**：原本的每日統計頁，內容不變
- **趨勢**、**生長曲線**：原本趨勢頁的兩種模式，內容不變
- 三種模式共用同一個頁首（標題「統計」＋寶寶切換）
- recharts 照舊 lazy load：只有切到「趨勢」或「生長曲線」才下載圖表 chunk，打開「每日」不會載入
  - 實作時發現既有問題：`manualChunks: { recharts: ['recharts'] }` 會把 react 一起拉進 recharts chunk，主程式為了 react 在啟動時就載入整個圖表庫（gzip 150 KB）。改成函式寫法、把 react 明確切到自己的 chunk 後，啟動時不再載入 recharts（gzip 105 KB），已用瀏覽器實測
- 舊的網址 hash 要能用：`#stats` → 統計／每日，`#trend` → 統計／趨勢（主畫面捷徑或書籤可能還留著舊的）

實作上把 `TrendPage` 內部的 `mode` state 往上提到新的 `StatsPage`，`DailyStatsPage` 和 `TrendPage` 各自變成不帶頁首的內容元件。兩者的測試不用改。

## 4. 資料模型

### 4.1 副食品紀錄 `FoodRecord`

```ts
interface FoodRecord {
  id: string;            // UUID，小寫
  babyId: string;
  timestamp: number;     // epoch ms，與 RecordData 同一種存法
  foods: string[];       // 食材名稱，至少一個、不重複
  firstFoods: string[];  // 存檔當下還是「未嘗試」的食材（foods 的子集）
  amount?: { value: number; unit: '匙' | 'ml' | 'g' };
  reactions: Reaction[]; // '紅疹' | '腹瀉' | '嘔吐' | '便秘' | '脹氣'
  note?: string;
}
```

和 babyfoodie 的差別：

- 日期＋時間兩個字串合成一個 `timestamp`，跟現有記錄一樣，排序、跨日分組都沿用既有工具
- 拿掉 `createdAt` / `updatedAt`：同步層的 outbox 已經記錄修改時間，資料本身不需要
- `firstFoods` 照 babyfoodie 在存檔時決定、存下來，不在顯示時重算。重算的話，開始用 App 前就手動標成「已嘗試」的食材會被誤標「第一次」

### 4.2 試敏標記 `FoodMark`

```ts
interface FoodMark {
  key: string;     // "{babyId}|{食材名稱}"，與接種紀錄的 key 同一種組法
  babyId: string;
  food: string;
  status: 'untried' | 'tried' | 'reaction';
}
```

只有手動改過狀態的食材才有一筆。食材狀態的判斷規則照 babyfoodie：

1. 有手動標記 → 用手動標記（手動選「未嘗試」也算，會蓋過紀錄）
2. 沒有手動標記 → 有任何紀錄含這個食材就是「已嘗試」，否則「未嘗試」

刪掉紀錄後，某食材已經沒有紀錄、也沒有手動標記時，自然變回「未嘗試」，不需要額外處理。

### 4.3 自訂食材：不另外存，從資料推出來（已確認）

babyfoodie 把自訂食材另外存成一個清單。這次建議**不存**：試敏表的「其他」區直接列出「在這個寶寶的紀錄或標記裡出現過、但不在 118 項清單裡」的名稱，依第一次出現的時間排序。

- 好處：少一種同步資料，也不會有「清單裡有、但哪裡都沒用到」的孤兒資料
- 跟 babyfoodie 的差別：自訂食材所在的紀錄全刪掉、又沒有手動標記時，它會從「其他」區消失。babyfoodie 會留著

### 4.4 試敏表清單

- 118 項食材寫成 `web/src/logic/foods.ts`，內容照 babyfoodie 的 SPEC.md（已逐月核對過，含重複編號、跳號、刪掉「青菜」）
- 食材以名稱當識別（118 項名稱不重複）

### 4.5 儲存層

Dexie schema 3 → 4，新增兩張表：

```
foodRecords: 'id, babyId, timestamp'
foodMarks:   'key, babyId'
```

新增資料表屬於自動遷移，既有資料不動。兩張表都掛進 outbox middleware，寫入自動進同步佇列。

**刪除寶寶時一併刪掉**：`deleteBabyCascade()` 多刪這兩張表。

## 5. 同步

### 5.1 新的資料種類

`EntityKind` 從 `profile | record | vaccineDose` 加上 `foodRecord`、`foodMark`。要改的地方：

- `shared/validateEntity.ts`：新增 `validateFoodRecord`、`validateFoodMark`，web 的備份檔和伺服器共用同一份規則
- `server/src/sync.ts`：`KINDS` 加上兩種
- `web/src/sync/sync.ts`：`tableOf()` 對應到新的表，`applyRemote` 的 transaction 加上新的表

伺服器的 SQLite 用 `(kind, id)` 當主鍵、資料存 JSON，**不需要改資料表結構**。

### 5.2 舊版 App 的相容問題（重要）

兩支手機不會同時更新。如果伺服器先開始傳副食品資料，**還沒更新的舊版 App** 會出問題：舊版的 `tableOf()` 只認得三種，其他種類一律當成接種紀錄，會把副食品資料**寫進接種紀錄表**。

做法：

1. **客戶端在同步請求裡宣告自己認得的種類**：新版送 `kinds: ['profile', 'record', 'vaccineDose', 'foodRecord', 'foodMark']`
2. **伺服器只把對方宣告過的種類傳給它**。沒帶 `kinds` 的舊版只會收到原本的三種
3. **新版第一次啟動時，同步游標歸零、完整重拉一次**。舊版收不到副食品資料，游標卻已經走過去了；不重拉的話，更新後會永遠缺那幾筆。目前資料量小，完整重拉只要幾秒
4. 順手把 `tableOf()` 改成遇到不認得的種類就略過，不要再預設成接種紀錄，以後加新種類不會再踩到同一個坑

部署順序：**先更新伺服器，再更新網頁**。伺服器沒更新前，新版網頁上傳的副食品資料會被拒收、留在 outbox，伺服器更新後下一輪同步會自動補傳，不會遺失。

## 6. 備份檔

版本號**維持 2**，最外層多兩個選填陣列 `foodRecords`、`foodMarks`，沿用疫苗那次的策略：

- 舊版讀新檔：忽略不認得的欄位，不會整個檔案拒絕
- 沒用到副食品功能時，匯出的檔案和現在**逐字節相同**
- 匯入合併：`foodRecords` 以 `id` 聯集、`foodMarks` 以 `key` 聯集，重複時保留本機版本（與現有記錄、接種紀錄的規則相同）
- 匯入時寶寶 id 被重新對應的話，`foodRecords.babyId` 和 `foodMarks` 的 key 跟著改

## 7. 畫面與互動

「副食品」分頁上方用分段切換分成兩個檢視：

```
[ 紀錄 ][ 試敏表 ]
```

頁首與其他分頁相同：標題＋寶寶切換。寶寶月齡用現有的 `babyAge()`（月底 clamp 規則與 babyfoodie 相同）。

### 7.1 紀錄

**列表**

- 依日期分組（今天、昨天、9/17（四）），最新在上面
- 每張卡片：時間、食材（存檔時第一次吃的標「第一次」）、份量、反應
- 有反應的卡片用現有的 danger 色系標示
- 點卡片進入修改；列表上方是「新增副食品紀錄」按鈕（不做右下角浮動按鈕：會跟提示訊息與底部分頁列搶位置）

**填寫表單**：沿用記錄頁的做法，在同一頁展開表單，修改時自動捲到表單

| 欄位 | 規則 |
|---|---|
| 日期時間 | 預設現在，不能晚於現在 |
| 食材 | 必填，可複選。「最近吃過」和「目前月齡」的食材直接列成按鈕；其他的打字搜尋，搜不到可以直接新增（最多 20 字） |
| 份量 | 選填，數字＋單位（匙／ml／g），單位預設「匙」 |
| 反應 | 選填，勾選：紅疹、腹瀉、嘔吐、便秘、脹氣 |
| 備註 | 選填 |

- 存檔後，裡面的食材在試敏表自動變成「已嘗試」
- **有勾反應時**，存檔後跳出對話框問要把哪些食材標成「有反應」：只列出還不是「有反應」的食材，預設勾選這次第一次吃的
- 修改時可以刪除，刪除前確認
- 連點儲存只會存一筆（babyfoodie 修過的 bug，這邊一開始就要防）

### 7.2 試敏表

- 依月齡分區：4、5、6、7、8、9、10 個月，最後是「其他」（自訂食材）
- 每個食材顯示建議順序編號和名稱；同一區內依編號排序，同編號照原圖先後
- 三種狀態用**顏色加圖示**區分，不只靠顏色：

  | 狀態 | 外觀 |
  |---|---|
  | 未嘗試 | 白底 |
  | 已嘗試 | 綠底（`--color-success` 系）＋勾勾 |
  | 有反應 | 紅底（`--color-danger` 系）＋警示圖示 |

- 點食材從下方跳出選單，直接選「未嘗試／已嘗試／有反應」
- 標示目前月齡那一區（未滿 4 個月不標；10 個月以上標 10 個月）；切到試敏表時自動捲到那一區
- 上方月份跳轉列（4～10、其他），往下捲時固定在畫面頂端
- 「其他」區還沒有自訂食材時顯示：「新增紀錄時輸入表上沒有的食材，會出現在這裡。」

### 7.3 還沒有寶寶資料

沿用其他分頁的做法（`currentBaby` 為 null 時的提示），不另外設計。

## 8. 錯誤處理

- 寫入失敗（例如儲存空間滿）：顯示錯誤、保留表單內容，不關閉表單
- 試敏表改狀態失敗：還原成原本的狀態並提示
- 同步被伺服器拒收：沿用現有的同步狀態列（「N 筆變更被伺服器略過」）

## 9. 測試

- `foods.ts`：共 118 項、名稱不重複、各月份項數（34／9／14／26／12／9／14）、抽查幾個重複編號與跳號
- 食材狀態判斷：手動標記優先、刪紀錄後變回未嘗試、手動「未嘗試」蓋過紀錄
- 自訂食材推導：排除清單內食材、依第一次出現排序、跨寶寶不互相影響
- 「第一次」與「有反應」詢問的預設勾選
- 驗證規則：`shared/` 的向量檔加上兩種新資料，web 與伺服器都要跑過
- 同步：新種類的上傳與拉取；**舊版客戶端（不帶 `kinds`）收不到新種類**；新版首次啟動重拉後資料完整；`tableOf()` 遇到不認得的種類會略過
- 備份檔：沒用副食品時匯出逐字節不變；新欄位的匯出、匯入、合併、寶寶 id 重新對應
- 統計分頁：舊 hash `#trend`、`#stats` 對應到正確模式；打開「每日」不載入 recharts chunk

## 10. 上線步驟

1. 部署伺服器（`scripts/deploy-api.sh`）
2. 合併網頁的 PR，Cloudflare Pages 自動部署
3. 兩支手機都打開一次 App 確認更新，各自記一筆副食品，確認另一支看得到
4. 到 babyfoodie repo 的 Settings → Pages 關掉 GitHub Pages（需要使用者操作，這個環境沒有改 repo 設定的權限）。要不要把 repo 設成 archived 另外決定

## 11. 不做的事

- 不匯入 babyfoodie 的舊資料
- 不帶入 babyfoodie 的貼紙手帳風設計
- 副食品紀錄不進每日統計、趨勢圖。之後真的需要再加
- 副食品的反應（腹瀉、便秘）不跟記錄頁的大便紀錄連動
- 不做食材的營養資訊或食譜
